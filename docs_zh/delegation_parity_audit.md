# Delegation 对等审计

本次审计从四个第一性原理角度比较 `edgecrab` 与 Hermes：

1. 委托必须保持有界。
2. 上下文压力显示必须反映真实的提示压力，而不是误导性的子集。
3. 压缩警告必须保持信息丰富，同时不进入嘈杂或不稳定的循环。
4. 用户必须能够看到委托代理正在做什么，跨越 CLI 和网关路径。

## 已实施的修复

- 状态栏上下文令牌现在使用提示端压力（`input + cache_read + cache_write`）而不是 `input + output`。
- TUI 中的上下文窗口百分比现在被限制在 `100%`。
- 同回合的 `delegate_task` 爆发在调度前被限制，因此一个模型响应不能超出支持的并发限制。
- 委托子代理的推理现在通过事件管道流动。TUI 使用它来更新实时委托任务状态；网关仅在启用推理显示时才展示它。
- `delegate_task` 结果现在除了纯输入/输出计数外，还暴露了提示/缓存/推理令牌桶。

## 环境特定的测试矩阵

### 核心循环

- 单元测试：限制一个模型回合中过多的 `delegate_task` 调用，同时保留非委托调用和顺序。
- 单元测试：压缩警告触发一次，在成功压缩后重置，并且从不报告超过 `100` 的百分比。
- 单元测试：流式使用量在存在权威提供程序使用量时保留它，并在省略时回退到确定性估计。
- 集成测试：子代理取消在任何进一步的子工具调度之前从父中断传播。

### CLI / TUI

- 单元测试：状态栏使用提示端上下文令牌，并将百分比限制在 `100`。
- 单元测试：委托的推理/工具事件更新最新的活动子代理摘要，而不是淹没转录。
- 集成测试：长时间运行的委托任务保持稳定的状态栏和转录，没有重复的占位符行。
- 集成测试：恢复的会话从持久化的缓存/读取/写入桶中恢复提示压力计数器。

### 网关

- 单元测试：委托的启动、推理、工具批处理和完成消息保持有序且线程安全。
- 集成测试：类似 webhook 的平台抑制嘈杂的进度；支持编辑的平台接收渐进状态，没有重复的最终交付。
- 集成测试：中途压缩后的会话连续性保留压缩的转录，并且不会丢失摘要回合。

### 工具模态：`terminal`

- 集成测试：并行安全的委托终端/文件/网络混合为每个工具调用保留一个结果，即使一个任务崩溃或被取消。
- 集成测试：批准门控命令在委托运行内触发时仍能正确阻止。
- 集成测试：后台进程输出不会破坏委托进度渲染。

### 工具模态：`execute_code`

- 集成测试：委托子代理被阻止使用 `code_execution` 工具集，无论是通过请求的工具集还是继承的父工具集。
- 集成测试：父 `execute_code` 运行不会消耗委托子代理的迭代预算，反之亦然。
- 回归测试：没有共享进程/会话状态在委托代码或终端会话之间泄漏。

## 与 Hermes 相比的剩余差距

- `edgequake-llm` 仍然不在标准化的流式响应契约上暴露缓存写入令牌，因此会话会计只能在上游提供程序路径通过更高层提供它们时显示缓存写入令牌。
- EdgeCrab 现在跟踪一个显式的进程内 `last_prompt_tokens` 标量用于实时上下文压力显示，但它仍然不像 Hermes 那样在会话恢复之间持久化该值。
- 委托推理目前是实时状态信号，而不是完整的转录工件。这是 UX 的正确默认值，但 Hermes 在调整该噪音阈值方面有更多经过实战检验的历史。
